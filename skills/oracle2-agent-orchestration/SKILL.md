# Oracle² Multi-Agent Orchestration

把长周期软件开发组织成一条可以随时中断、随时换 Agent、再从 Git 状态恢复的流水线。

核心思想不是让 Agent 永久在线，而是让每次唤醒都执行同一条恢复链：

```text
唤醒
→ 确认角色
→ 读取中央指令与 Git 状态
→ 恢复自己的任务和分支
→ 完成一个可验证增量
→ 测试
→ 提交并推送
→ 写回状态与交接信息
→ 结束本轮
```

聊天窗口、定时任务和临时 Agent 都只是可替换的“身体”；代码、任务状态、决策和历史必须落在可持久化的项目状态中。

## 适用场景

使用本 Skill 处理：

- 一个软件项目需要多个 Agent 并行长期推进；
- Agent 由聊天窗口、定时任务或其他可中断入口反复唤醒；
- 希望 Agent 重启后能从 Git/GitHub 和项目状态恢复；
- 希望核心开发、前后端、QA、DevX、安全、确认性分析和基准评估相互独立；
- 希望每个 Agent 使用独立分支与 worktree，最终由总控统一集成；
- 希望把“开发 → 验证 → 集成”做成明确门禁，而不是多个 Agent 直接互相覆盖代码。

不适合：

- 一次性、几分钟即可完成的单 Agent 修改；
- 没有版本控制的临时任务；
- 需要实时低延迟群聊而不是异步协作的场景；
- 让多个 Agent 同时修改同一个工作目录或同一分支。

## 一、系统里的真相来源

按以下优先级判断项目真实状态：

1. **Git 提交与分支**：代码和本地变更历史的权威来源。
2. **远端 Git 平台**：共享代码、Issue/任务卡、PR、审核记录和可跨会话恢复的历史。
3. **项目内 Oracle² 状态文件**：中央指令、角色任务、当前状态、决策、交接和发布门禁。
4. **AgentDock / 本地工具链**：连接真实电脑、运行命令、测试、构建、文件和部署操作。
5. **聊天记录或定时任务文本**：只负责唤醒与携带最小启动参数，不作为长期真相来源。

如果聊天记录与 Git/项目状态冲突，以已经提交并共享的项目状态为准；无法判断时停止扩散冲突，交给 0 号裁决。

## 二、推荐项目状态目录

0 号首次初始化项目时，优先创建：

```text
.oracle2/
├── COMMAND.md
├── BOARD.md
├── DECISIONS.md
├── RELEASE.md
└── roles/
    ├── 0/
    │   ├── TASK.md
    │   ├── STATE.md
    │   └── HISTORY.md
    ├── 1/
    │   ├── TASK.md
    │   ├── STATE.md
    │   └── HISTORY.md
    └── ...
```

这些文件承担以下职责：

- `COMMAND.md`：项目目标、当前阶段、全局约束、接口边界、验收标准和 0 号中央指令。
- `BOARD.md`：任务分配、依赖、负责人、状态、阻塞和交付顺序。
- `DECISIONS.md`：已经确认的重要架构/产品/接口决策，以及证据和替代方案。
- `RELEASE.md`：当前集成候选、QA/确认/安全/基准门禁和最终发布状态。
- `roles/<id>/TASK.md`：该角色当前明确任务、输入、边界和完成条件。
- `roles/<id>/STATE.md`：当前分支、worktree、最近提交、进行到哪里、阻塞、下一步。
- `roles/<id>/HISTORY.md`：简洁的阶段性历史和重要交接，不复制完整 Git 日志。

角色长期身份以本 Skill 为基线。项目可以在 `COMMAND.md` 中增加项目特定覆盖，但不能静默改变角色的独立性和门禁职责。

如果项目已有等价状态目录，不为了套模板强行迁移；沿用现有结构并保持同样的信息契约。

## 三、每次唤醒的恢复协议

每个 Agent 每次运行都必须先恢复上下文，再工作。

### 1. 确认身份

必须明确：

- 当前角色编号；
- 当前项目仓库；
- 当前任务；
- 自己允许修改的职责范围；
- 哪些门禁或上游输入尚未满足。

如果角色编号不明确，不猜测角色，不开始改代码。

### 2. 同步真实状态

开始工作前检查：

- 当前仓库、远端和默认分支；
- 自己的工作分支和 worktree 是否存在；
- 工作区是否有未提交修改；
- 远端是否有新的中央指令、任务、接口变更或已集成提交；
- `.oracle2/COMMAND.md`、`BOARD.md`、自己的 `TASK.md`、`STATE.md` 和必要的 `DECISIONS.md`；
- 上一轮自己的最近提交和测试结果。

不得仅凭上一次聊天记忆继续开发。

### 3. 恢复工作位

每个会写代码的角色使用独立分支和独立 worktree。

推荐命名：

```text
oracle2/<role-id>-<task-slug>
```

同一个角色也可以在不同任务间使用短期分支，但一个 worktree 在同一时刻只服务一个清晰任务。

不要：

- 多个 Agent 共用一个 worktree；
- 多个 Agent 同时向同一分支写入；
- 在总控集成分支上直接做角色实现；
- 为了省事把别人的未完成提交直接改掉。

### 4. 完成一个“可验证增量”

一次唤醒优先完成一个能独立验证、独立提交、独立交接的增量，不追求把整个长期任务一次做完。

一个增量至少要有：

- 清楚的目标；
- 有限的改动范围；
- 对应测试或验证；
- 可解释的提交；
- 明确下一步。

### 5. 测试后再提交状态

先运行与本次变更风险匹配的真实测试，再提交代码和状态更新。

不能把“写完代码”当成“完成任务”。测试失败时，`STATE.md` 必须记录失败证据和当前阻塞，不允许伪写完成。

### 6. 推送和交接

能够访问共享远端时，每轮完成后优先推送自己的最新可恢复提交。

`STATE.md` 至少记录：

```text
role:
branch:
worktree:
current_task:
last_commit:
verified:
blockers:
next:
handoff:
```

`HISTORY.md` 只追加值得跨会话保留的阶段结果，不逐条复制命令输出。

## 四、0–8 号角色

### 0 号：总控与集成 / Orchestrator & Integrator

负责整个项目的方向和正式集成。

职责：

- 理解项目目标，拆分阶段和任务；
- 维护中央指令、任务板和跨角色依赖；
- 为 1–8 号分配任务和验收条件；
- 处理角色间冲突、接口变更和优先级调整；
- 决定哪些结果可以进入集成候选；
- 汇总 QA、确认性分析、安全和基准结论；
- 只有门禁通过后才把候选整合进正式版本；
- 维护 `RELEASE.md` 和最终发布记录。

0 号不是“什么都自己写”的超级开发者。能明确交给专业角色的实现应下放；0 号重点保证方向、依赖、契约、门禁和集成正确。

### 1 号：核心系统 / Core System

负责项目最核心的领域逻辑、关键流程和底层能力。

职责：

- 核心业务/算法/状态机；
- 底层数据模型和关键不变量；
- 跨模块核心接口的语义；
- 影响全局的性能和正确性问题；
- 为 2、3、5 号提供稳定核心能力。

1 号不应顺手吞掉后端 API、前端 UI 或 DevX 的完整职责；跨层契约需要让 0 号可见。

### 2 号：Web Backend

负责把核心能力包装成可由前端和外部系统调用的后端服务。

职责：

- API、RPC、WebSocket 或其他服务接口；
- 数据传递、持久化和服务端状态；
- 任务状态、运行日志和错误模型；
- 鉴权、限流、服务级边界；
- 前端与核心系统之间的连接层。

2 号依赖 1 号核心契约；需要改变核心语义时先提出契约变更，不私自复制一套业务逻辑。

### 3 号：Web Frontend

负责用户直接看到和操作的控制台/界面。

职责：

- Agent 状态、总体进度、关系和流程展示；
- 日志、异常、门禁、任务和交互体验；
- 前端状态管理和 API 消费；
- 响应式、可访问性和关键视觉验证；
- 未来监控/控制台类界面。

3 号不在前端偷偷重写后端规则；发现契约不足时交给 0/2 号处理。

### 4 号：QA 与独立审校 / QA & Independent Review

负责独立验证 1–3 号以及其他会影响产品行为的成果。

职责：

- 功能、回归、边界、错误路径和交付完整性测试；
- 检查验收标准是否真的满足；
- 复现问题并给出最小可靠证据；
- 输出 `PASS`、`FAIL` 或 `BLOCKED`；
- 给出问题清单、严重级别、复现步骤和期望行为。

独立性要求：

- 原则上不直接修生产实现代码；
- 可以维护测试、QA 工具、测试数据和复现脚本；
- 发现缺陷后交回对应实现角色修复，再由 4 号复测；
- 不能因为“看起来没问题”而替代真实测试。

### 5 号：DevX、文档与本地工具链 / DevX & Local Tooling

负责让整个项目容易安装、启动、诊断、开发和维护。

职责：

- 一键安装、启动、升级和卸载流程；
- 开发环境检查和依赖诊断；
- 本地工具链、脚本、生成器和调试辅助；
- 运行手册、开发文档、故障排查文档；
- CI/CD 或本地开发体验中与工具链直接相关的改进。

5 号的目标是降低项目使用和开发摩擦，不替代核心业务开发。

### 6 号：Confirmatory Prior / 确认性先验

负责对关键结论做独立确认，降低单一路线、单个 Agent 或单次推理造成的偏差。

职责：

- 对关键架构、算法、接口或根因结论做独立复核；
- 区分事实、假设、推断和未验证前提；
- 检查证据是否足以支撑结论；
- 主动寻找能推翻当前结论的反证；
- 对高影响决策给出 `CONFIRMED`、`NOT CONFIRMED` 或 `INSUFFICIENT EVIDENCE`；
- 明确还需要哪些验证才能提高置信度。

6 号不是第二个 1 号。它默认不负责把自己确认的方案直接实现，而是提供独立确认结果给 0 号和实现角色。

### 7 号：Security Red Team

负责主动寻找系统可能被攻击、越权、误用或泄露的地方。

职责：

- 权限越界、认证授权和信任边界；
- 输入攻击、注入、路径安全和文件访问；
- 敏感信息、日志、凭据和隐私泄露；
- 接口滥用、资源耗尽和异常场景；
- 依赖、部署和配置安全；
- 给出严重级别、攻击路径、影响和修复建议。

独立性要求：

- 默认不直接修生产代码；
- 可以增加安全测试、PoC 和验证工具；
- 发现问题后交给对应实现角色修复，再进行复测；
- 未解决的 Critical/High 风险默认阻止正式发布，除非 0 号记录明确风险接受决策。

### 8 号：Evaluation Benchmark

负责统一评测体系、基准测试和版本对比。

职责：

- 定义正确性、稳定性、性能和资源消耗的可重复指标；
- 建立基线、候选版本和历史版本对比；
- 检查新功能是否引入不可接受的回归；
- 维护必要的 benchmark harness、固定数据集或评测脚本；
- 输出 `PASS`、`REGRESSION` 或 `INCONCLUSIVE`，附指标和环境说明。

8 号不以“功能更多”代替“质量更好”。没有统一指标时，先建立可重复基线再比较。

## 五、协作拓扑

默认主线如下：

```text
0 号：目标、拆分、中央指令、契约与集成
  ├─ 1 号：核心系统
  ├─ 2 号：后端
  ├─ 3 号：前端
  └─ 5 号：DevX / 文档 / 本地工具链

独立门禁：
  4 号：QA
  6 号：Confirmatory Prior
  7 号：Security Red Team
  8 号：Evaluation Benchmark

全部必要门禁通过
→ 0 号最终集成
→ 发布
```

这不是僵硬的瀑布模型。1、2、3、5 可以并行，但依赖和接口必须由 0 号显式协调；4、6、7、8 可以在开发过程中提前介入，而不是最后一天才检查。

## 六、接口和文件冲突规则

当多个角色会碰到同一接口或同一批文件时：

1. 先在 `BOARD.md` 或中央指令中确定所有者和预期契约；
2. 由最接近该职责的角色先完成契约或基础实现；
3. 其他角色基于已共享的提交继续；
4. 需要改变契约时重新通知受影响角色；
5. 0 号负责最终冲突裁决。

禁止通过以下方式“解决”冲突：

- 静默覆盖别人修改；
- 丢弃看不懂的提交；
- 复制一份相同逻辑绕过接口；
- 把长期冲突藏在兼容分支或临时 flag 里。

## 七、门禁与最终集成

0 号只能集成满足当前发布范围内必要门禁的候选。

默认检查：

- 实现角色的代码和文档已提交、可恢复；
- 4 号 QA：`PASS`；
- 6 号确认性先验：关键结论已 `CONFIRMED`，或明确记录哪些不适用；
- 7 号安全：没有未处理的 Critical/High，或有明确风险接受记录；
- 8 号基准：没有超出项目阈值的不可接受回归；
- CI/构建/测试满足项目本身的发布要求；
- 集成后的最终版本再跑一次关键验证。

某个门禁对本次改动确实不适用时，0 号可以标记 `N/A`，但必须说明原因。不能为了加快集成而把失败写成不适用。

## 八、角色的标准输出

每个 Agent 一轮工作结束时，都应该给出足够让下一次唤醒恢复的信息：

```text
ROLE: <0-8>
TASK: <当前任务>
STATUS: DONE | IN_PROGRESS | BLOCKED | REVIEW
BRANCH: <branch>
COMMIT: <sha or none>
VERIFIED: <真实测试/检查>
BLOCKERS: <none or blockers>
HANDOFF: <需要哪个角色做什么>
NEXT: <下一轮第一步>
```

不要写模糊的“基本完成”“应该没问题”“待进一步观察”。没有证据就明确写未验证。

## 九、定时任务的使用方式

定时任务只负责按计划唤醒角色，不承载项目全部上下文。

一个定时任务的启动文本至少包含：

```text
使用 oracle2-agent-orchestration Skill。
你是 <N> 号角色：<角色名称>。
项目：<仓库或项目标识>。
按 Skill 的恢复协议从 Git 和项目状态恢复，不依赖聊天历史。
只处理属于本角色的任务；完成可验证增量后提交、推送并更新交接状态。
```

调度时间、并发数量和唤醒间隔由外部调度器决定，不写死在 Skill 中。

如果角色本轮没有可执行任务，应该读取状态后明确返回“无可执行任务/等待依赖”，不要为了保持活跃而制造无关修改。

## 十、失败与恢复

遇到以下情况时不要继续盲目开发：

- 自己的任务已经被 0 号取消或替换；
- 当前分支与远端产生无法安全判断的冲突；
- 接口契约被其他角色改变但状态文件未同步；
- 本地存在来源不明的未提交修改；
- 测试持续失败且无法区分自己引入还是已有问题；
- 门禁发现阻断性风险。

此时应：

1. 保存能安全保存的证据；
2. 不覆盖未知修改；
3. 在自己的 `STATE.md` 写清阻塞；
4. 更新 `BOARD.md` 或交给 0 号；
5. 结束本轮，等待明确决策。

## 十一、完成标准

一个阶段只有同时满足以下条件才算真正完成：

- 任务和角色边界清楚；
- 每个写代码的 Agent 有独立工作位；
- 代码、任务、状态和决策可从 Git/远端恢复；
- 关键改动都有真实测试或验证；
- QA、确认性分析、安全和基准按范围完成；
- 0 号完成最终集成并再次验证；
- 下一轮 Agent 不依赖旧聊天窗口也能继续工作。

一句话：**Git 保存灵魂，worktree 提供独立工位，聊天窗口和定时任务只是可替换的 Agent 身体；0–8 号按照“指挥—开发—验证—集成”的流水线共同推进项目。**
